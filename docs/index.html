它是怎么工作的

四个阶段，中间任何一步失败都不会被悄悄跳过。

  1. 规划

    先输出结构化 JSON 计划（假设 + 步骤），而不是直接乱改文件。

  2. ReAct 工具循环

    模型自己选择每次工具调用，观察结果后决定下一步。

  3. 独立验证

    由 harness 自己运行真实测试并回读结果，不采信模型的自我陈述。

  4. 反思 → 长期记忆

    记录根因与教训，供下一次任务召回。

边界条件是被写进架构的，不是靠提示词祈祷

前提很明确：模型的输出不可靠。所以每一类失败都有对应的处理。

  • 跑不完 — 迭代次数硬上限（默认 12，可配置到 50）
  • 陷入死循环 — 字节归一化的重复检测 + 两次调用成环检测 + 无进展追踪
  • 工具参数是垃圾 — 任何 handler 执行前先过 JSON Schema 校验
  • 补丁打到错的地方 — 精确匹配失败后走空白容忍匹配，有歧义就拒绝写入
  • 跑出工作区 — 每个路径都会被解析并限制在工作区根目录内，危险命令拦截，写文件与执行命令二次确认
  • 钱烧超了 — token 预算节流器 + 用量先预留后结算

跑起来

两步，不需要额外配置。

git clone https://github.com/BOHAOYUAN/CodeBuddy.git
cd CodeBuddy && npm install

npm test            # 62 个单元测试，约 1 秒
npm run typecheck   # TypeScript 严格校验
npm start           # 用 CLI 跑一次真实修复任务

需要在工作区 .env 里填一个 OpenAI 兼容的接口地址与 Key （PROVIDER_BASE_URL / PROVIDER_API_KEY / PROVIDER_MODEL）， .env.example 里有全部可调参数。

我知道它哪里不行

这些限制我自己写在 README 里，因为知道自己系统的坏点也是系统的一部分。

评测基准很小：每个任务都是一个函数 + 一个测试文件，没有验证过多文件改动或构建流程。
反思可能写错：长期记忆里的教训由模型生成，即使修复成功，记录的根因也可能是错的——需要更严格的写入闸门，目前尚未实现。
只测过一个模型家族：所有数据来自 openai/gpt-oss-120b，换模型的真实表现未测量。
扩展目前只在自己的目录内工作，还不会去修用户的项目——这是刻意的范围边界，不是已完成的功能。
